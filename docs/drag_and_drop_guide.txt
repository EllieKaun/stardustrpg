================================================================================
  ЧАСТЬ 1. КАК УСТРОЕН КАДР В GAMEMAKER
================================================================================

Каждый кадр (60 раз в секунду) GameMaker проходит события в таком порядке:

  1. Begin Step    — у ВСЕХ инстансов
  2. (алармы, клавиатура/мышь-события объектов, если используются)
  3. Step          — у всех инстансов
  4. End Step      — у всех инстансов
  5. Draw Begin / Draw / Draw End   — рисование в мире (комната, камера)
  6. Draw GUI Begin / Draw GUI / Draw GUI End — рисование интерфейса
                   поверх всего, в координатах экрана (GUI), камера не влияет

Почему это важно для драга:

  * Порядок инстансов ВНУТРИ одного события не гарантирован. Если менеджер
    драга и декбилдер оба обрабатывают мышь в Step, неизвестно, кто первый.
    Решение: менеджер обрабатывает мышь в BEGIN STEP. Тогда к моменту Step
    декбилдера менеджер уже решил «идёт перетаскивание или нет», и панель
    может это проверить.

  * Карта в руке должна рисоваться ПОВЕРХ всех панелей. Panel.draw() рисует
    слоты внутри клипа (на поверхность — см. guiClipBegin/guiClipEnd), всё,
    что выходит за край панели, обрезается. Если рисовать летящую карту там —
    её обрежет. Решение: рисовать её в событии DRAW GUI END отдельного
    объекта-менеджера. Оно идёт после всех Draw GUI, значит поверх всего.

  Как добавить событие в IDE: открыть объект → Add Event →
    Step → Begin Step
    Draw → Draw GUI End

  ЧАСТЬ 2. СИСТЕМНЫЕ ФУНКЦИИ И ПРИЁМЫ GML

2.1. Мышь
---------
device_mouse_x_to_gui(0), device_mouse_y_to_gui(0)
    Позиция мыши в координатах GUI-слоя (0,0 — левый верхний угол экрана,
    размер = display_get_gui_width/height). Декбилдер и рука в бою рисуются
    в GUI, поэтому для них берём ЭТО. Аргумент 0 — номер устройства (мышь/
    первый палец).

mouse_x, mouse_y
    Позиция мыши В МИРЕ (в комнате, с учётом камеры). Нужна, когда цель —
    инстанс в комнате (враг в бою). Не путать с GUI!

mouse_check_button_pressed(mb_left)   — true ТОЛЬКО в кадр нажатия.
mouse_check_button(mb_left)           — true, пока кнопка зажата.
mouse_check_button_released(mb_left)  — true ТОЛЬКО в кадр отпускания.
    Драг — это как раз связка: pressed (начало) → check (держим) → released
    (бросили). mb_right — правая кнопка (удобно для отмены).

keyboard_check_pressed(vk_escape)     — Esc в этот кадр.

2.2. Геометрия
--------------
point_distance(x1, y1, x2, y2)  — расстояние. Нужно для «порога драга»:
    пока мышь сдвинулась от точки нажатия меньше порога — это ещё клик.
pointInRect(px, py, rx, ry, rw, rh) — (наш, scrDeckBuilderDrawing) попадание.
pointInRotatedRect(px, py, cx, cy, w, h, angle) — (наш, scrDrawing) то же для
    наклонённой карты (рука в бою).
position_meeting(x, y, obj_or_inst) — есть ли инстанс в точке МИРА
    (по его маске столкновения). Так бой ищет цель под курсором.

2.3. Плавность
--------------
lerp(a, b, t)  — линейная интерполяция: a + (b - a) * t.
    Каждый кадр x = lerp(x, targetX, 0.35) — объект «догоняет» цель,
    быстро в начале и мягко в конце. Так делаем движение летящей карты,
    возврат на место и «примагничивание» к слоту.
clamp(v, min, max) — ограничить значение.
sign(v) — знак (-1/0/1), удобно для наклона карты по направлению движения.

2.4. Рисование
--------------
display_get_gui_width()/height() — размер GUI. У нас меняется (setCrispGui),
    поэтому все пороги/размеры считать от него (или от panel.uiScale).
draw_set_alpha(a), draw_set_color(c) — ГЛОБАЛЬНОЕ состояние рисования.
    Всегда возвращай обратно (draw_set_alpha(1), draw_set_color(c_white)),
    иначе испортишь всё, что рисуется после тебя. В проекте так делают везде.
draw_rectangle(x1, y1, x2, y2, outline) — подсветка слота (outline=true — рамка).
draw_sprite_stretched(spr, img, x, y, w, h) — спрайт в прямоугольник.
drawCardFace(...) — (наш) карта по центру с углом/масштабом/прозрачностью.

2.5. Структуры, конструкторы, методы
------------------------------------
Конструктор:
    function DragManager() constructor { state = 0 }
    var m = new DragManager()
  Поля объявляются как обычные присваивания внутри.

static в конструкторе:
    static update = function() { ... }
  Метод создаётся ОДИН раз и общий для всех экземпляров (как у Panel).
  Без static каждый new создаёт свою копию функции.

Доступ к полю по строке и значение по умолчанию:
    _config[$ "onDrop"] ?? undefined
  [$ "key"] — чтение поля структуры по имени (не падает, если поля нет —
  вернёт undefined). ?? — «если слева undefined, возьми справа».

ВАЖНО про self и привязку методов (здесь чаще всего ошибаются):
  Функция, объявленная ВНУТРИ литерала структуры { ... onSlotClick: function() {...} },
  привязывается к ЭТОЙ структуре. Внутри неё self — это структура-конфиг,
  а не oDeckBuilder. Поэтому в Create_0.gml декбилдера колбэки пишут
      with (oDeckBuilder) { ... }
  чтобы вызвать код «от лица» декбилдера (доступ к editingCharacter,
  deckPanel и т.д.). Делай так же в своих колбэках источников/целей,
  либо явно привязывай: method(oDeckBuilder.id, function() {...}).

  method(context, func) — вернуть функцию, привязанную к context.
  with (obj) { ... }    — выполнить блок от лица инстанса(ов) obj.

================================================================================
  ЧАСТЬ 3. АРХИТЕКТУРА
================================================================================

Цель: менеджер драга НИЧЕГО не знает про колоду и бой. Он умеет только:
«под курсором есть что взять?» → «тащим» → «под курсором есть куда бросить?»
→ «бросили / отменили». Всё знание про колоду — в маленьких адаптерах.

Четыре понятия:

  ГРУЗ (payload) — что тащим. Обычная структура:
      {
          kind:   "card",            // тип груза: потом можно таскать не только карты
          card:   <struct Card>,     // для отрисовки
          ref:    { id, rarity },    // для логики
          source: <источник>,        // откуда взяли (чтобы вернуть / знать контекст)
          data:   { slotIndex: 3 }   // что угодно, что нужно источнику
      }

  ИСТОЧНИК (source) — откуда можно взять. Структура с функциями:
      hitTest(gx, gy)       → payload или undefined   (что под курсором)
      onDragStart(payload)  → (например, спрятать карту в слоте)
      onDragEnd(payload, dropped) → (вернуть отображение)

  ЦЕЛЬ (target) — куда можно бросить. Структура с функциями:
      hitTest(gx, gy)          → ctx или undefined (например {slotIndex: 5})
      accepts(payload, ctx)    → true/false (можно ли сюда)
      onDrop(payload, ctx)     → true/false (выполнить действие)
      drawHighlight(payload, ctx, ok) → (необязательно: подсветка)

  МЕНЕДЖЕР (oDragManager) — один объект. Хранит списки источников и целей,
  состояние и текущий груз. Каждый кадр:

      Idle ──(нажали ЛКМ над источником)──► Pressed
      Pressed ──(отпустили, не сдвинув)──► Idle         = это был КЛИК
      Pressed ──(сдвинули дальше порога)──► Dragging    = начался ДРАГ
      Dragging ──(отпустили над целью, accepts=true)──► onDrop → Idle
      Dragging ──(отпустили мимо / ПКМ / Esc)──► Returning
      Returning ──(карта долетела обратно)──► Idle

Почему «Pressed» отдельно: чтобы обычный клик не превращался в драг
от дрожания руки, и чтобы старое поведение «клик = добавить/убрать» работало.

Почему регистрация, а не жёсткий код: декбилдер при открытии регистрирует
свои источники/цели, при закрытии снимает. Бой сделает то же со своими.
Менеджеру всё равно, кто его использует.

Скелет Begin Step:

              // pressX/Y = gx/gy; state = DragState.Pressed
              // В Pressed переходим ВСЕГДА, даже без груза: иначе клик по пустому
              // слоту не распознается как клик (wasClick) и панель не выделит слот.

              // начался драг (только если было что брать)
              // payload.source.onDragStart(payload)
              // ghostX/Y = центр слота-источника (payload.data.rect), ghostW/H = его размер
              // homeX/Y = тот же центр
              state = DragState.Dragging
          }
          break

      case DragState.Dragging:
          // 1) карта едет за мышью: ghostX = lerp(ghostX, gx, 0.5) и т.д.
          // 2) найти цель под курсором: пройти targets, hitTest(gx, gy)
          //    → hoverTarget, hoverCtx; hoverOk = hoverTarget.accepts(payload, hoverCtx)
          // 3) отмена: mouse_check_button_pressed(mb_right) || keyboard_check_pressed(vk_escape)
          //    → cancel(); если это был Esc — consumedEscape = true
          // 4) отпустили ЛКМ (mouse_check_button_released(mb_left)):
          //    если hoverTarget != undefined && hoverOk:
          //        var ok = hoverTarget.onDrop(payload, hoverCtx)
          //        payload.source.onDragEnd(payload, ok)
          //        если ok: payload = undefined; state = Idle
          //        иначе: state = Returning
          //    иначе: state = Returning (и onDragEnd(payload, false) — см. cancel)
          break

      case DragState.Returning:
          // ghostX = lerp(ghostX, homeX, 0.3), то же для Y
          // когда point_distance(ghostX, ghostY, homeX, homeY) < 1 → payload = undefined; state = Idle

  }

Шаг 4.6. Панель: клик на отпускании, а не на нажатии
--------------------------------------------------------------------------------
Проблема: Panel.stepMouse вызывает onSlotClick на mouse_check_button_pressed.
Если ничего не менять — при начале драга из коллекции карта сразу
добавится в колоду кликом, а потом ещё и перетащится.

Решение (в Panel.stepMouse, scrDeckBuilderDrawing.gml):
  * Вкладки оставь на pressed — их не таскают.
  * Для слотов вместо clicked используй «клик от менеджера»:
        var slotClicked = instance_exists(oDragManager) ? oDragManager.wasClick
                                                        : mouse_check_button_pressed(mb_left)
    Менеджер ставит wasClick в кадр ОТПУСКАНИЯ, если мышь не сдвинулась.
  * Пока менеджер тащит (oDragManager.state == DragState.Dragging или Returning) —
    не обрабатывать наведение и клики вообще (return в начале stepMouse).
    Колесо прокрутки можно оставить — пусть листается во время драга.

Тонкость: wasClick говорит «был клик», но не «по какому слоту». Панель
сама смотрит, над каким слотом курсор (hoverSlot) — это тот же слот, где
нажали, потому что курсор почти не двигался. Этого достаточно.

Проверка: клик по картам работает как раньше (но на отпускании).

Шаг 4.8. Esc, Tab и обучение
--------------------------------------------------------------------------------
Esc: oGameController/Step_0.gml по Esc закрывает декбилдер. Если драг
отменён Esc'ом — декбилдер закрываться не должен. Менеджер в Begin Step
ставит consumedEscape = true, а в oGameController перед обработкой Esc:
  if (instance_exists(oDragManager) && oDragManager.consumedEscape) { /* пропустить */ }
Именно поэтому менеджер — в Begin Step: он успевает раньше Step контроллера.

Tab / закрытие: closeBuilder() вызывает cancel() и unregisterAll() —
иначе карта «повиснет» в воздухе над закрытым окном.

Обучение декбилдера: пока идёт (global.deckTutorialStage == DeckTutorialStage.Steps),
Step декбилдера выходит раньше. Менеджер тоже не должен работать:
в hitTest источников декбилдера верни undefined, если обучение активно
(или не регистрируй источники, пока оно идёт).

    - пройти cardHitRects (их заполняет Draw_64 боя) С КОНЦА: выбранная

  Карта в руке — в GUI. Враги — инстансы в МИРЕ. Для целей используй

  Менеджер передаёт в hitTest GUI-координаты — цель-враг их просто
  игнорирует и берёт mouse_x/mouse_y. Это нормально: интерфейс один,
  реализация своя.

6.4. Цели по типу карты (card.target):

  accepts(payload, ctx) проверяет, что тип цели подходит payload.card.target.

6.5. onDrop — НЕ играть карту самому!

      unselectTargets()

  Тогда стоимость, анимации, эффекты, обучение боя — всё отработает как
  обычно. Драг — просто ещё один способ ввода.

6.6. Подсветка цели: при наведении ставь enemy.isTarget = true (как
  selectNextTarget), при уходе — unselectTargets(). Тогда враг
